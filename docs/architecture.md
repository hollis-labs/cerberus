# Architecture: Cerberus on Substrate

This describes the `substrate-port` branch. The live build is on `main` until cutover. The plan is
`docs/substrate-port-plan.md`; the guide is hollis-labs/substrate `docs/adopting-substrate.md`. This file grows
with each slice and states only what the branch does now.

## Decisions (guide section 0)

| Question | Answer |
|---|---|
| Migrated data or fresh start? | **Migrated.** The app is in daily use; every store reaches the new build, verified (plan section 5; `docs/substrate-port/inventory-data.md`). The new build never opens the old data in place: the import is `cerberus migrate-from` (slice 10). |
| Variant | `app-host`: one process serves the API, the console, MCP over HTTP and the supervision loop. |
| Who issues identity? | Cerberus's own (`identity` module), owner created offline. Lands in slice 4. |
| Routes | Every `/api/` route has a scope (plan section 4.3); `/healthz` is the only public route. The outpost device protocol and event-token endpoints are open mounts that authenticate their own callers. |
| Background work | Supervision monitor, host probes, scheduler, event export, plugin processes. App code owns them and joins them before modules stop (plan section 4.4). |
| UI | app-shell plus BOM-pinned kits; app nav and surfaces in `ui/app.json` (slice 11). |
| Database | **SQLite only.** A `database.driver` other than `sqlite` is refused at start. |

## Layout (slices 1 and 2)

| Path | What |
|---|---|
| `cmd/cerberus/substrate.yaml` | The manifest: `app-host`, profile `minimal` plus `database` and `cli`; defaults for every key. |
| `cmd/cerberus/substrate_wiring.go` | Generated by `substrate generate`, committed. `go build` needs no substrate CLI. |
| `cmd/cerberus/main.go` | Signal context (SIGINT, SIGTERM), `boot.StartWith`, the `cli` root with `serve` (also the default command). |
| `cmd/cerberus/config.go` | The boot hooks: data directory and path anchoring (`AfterConfig`), the legacy guard (`Before["database"]`). |
| `cmd/cerberus/serve.go` | `serve`: loopback check, `httphost.Handler`, `httphost.Serve`; drains on signal. |
| `internal/settings` | Decodes the `cerberus:` block; refuses unknown keys and bad values, naming the key. |
| `internal/datadir` | Resolves the data directory and refuses the old build's state (`RefuseLegacy`). |
| `internal/storage` | The schema: one embedded goose migration (`migrations/sqlite/00001_schema.sql`), registered with `database.UseMigrationFS` in `main.go`, plus typed functions for pause state, applied digests and credential-issuance receipts. |
| `internal/registry` | Descriptor discovery and validation, carried; `ForRoot(adopt_root)` is the Substrate build's entry point (see Registry). |

The rest of `internal/` and `pkg/` is the old build's code, carried unchanged until its slice moves it
(plan section 4.2). The old `cmd/cerberus` entry and its CLI are removed from this branch; they stay readable on
`main`.

## Data directory

`CERBERUS_DATA_DIR`, otherwise the XDG data home joined with `cerberus-substrate`
(`~/.local/share/cerberus-substrate`, a sibling of the old build's `~/.local/share/cerberus`). Resolved in the
`AfterConfig` hook. A relative path in the config (the manifest default `database.sqlite.path: cerberus.db`) is joined
onto it; an absolute path from the override is kept; a relative path that leaves the directory is refused.

The directory is created `0700` only if it is missing. An existing directory is never changed: one that others can
read or enter is refused with the `chmod` to run. The database file is likewise created `0600` only if missing, and
an existing one with a looser mode is refused.

The directory never overlaps the old build, so both run side by side: the old build keeps `~/.cerberus` (state
tree) and `~/.local/share/cerberus` (its `workspaces/<ws>/main.db`).

### Legacy guard

`internal/datadir`. A refused start changes nothing, under the old homes or anywhere else: every check runs before
anything is created, and none of them writes.

In `AfterConfig`, before the data directory is created:

- `RefuseOldPaths`: the data directory or the database path is, or is inside, either of the old build's homes:
  `~/.cerberus` and the old XDG data directory (the XDG data home's `cerberus`). Symlinks are followed.
- `RefuseOldContents`: the data directory holds `workspaces/` (the old XDG layout) or an entry of the old state
  tree (`daemon.lock`, `cerberus.sock`, `cerberus.pid`, `registry.yaml`, `plugin-connectors.json`, `audit`,
  `approvals`).

In `Before["database"]`, immediately before the module opens (and would migrate) the file: the path check again,
then `RefuseOldSchema`. An existing file is opened `mode=ro&immutable=1`: no lock, no WAL replay, no checkpoint, and
no `-wal` or `-shm` created or removed. It is refused if it has a `schema_migrations` table (the old store's; goose
never creates one), or if it cannot be read that way.

## Database

SQLite only, opened by the `database` module (`database.From(app)`, libs `core/store`). The schema is one goose
migration until the first release; after that, changes go in new numbered files. The module migrates under its open
lock, so a start on an empty data directory creates the schema and a second start is a no-op (tested in
`internal/storage` and with the real binary in `cmd/cerberus`).

| Table | From the old build | Notes |
|---|---|---|
| `host_samples`, `host_status`, `host_sample_rollups`, `host_rollup_state`, `host_events` | `main.db`, same columns (migrations 006 to 008) | A test compares every column with the old migrations (frozen in `internal/storage/testdata/old`). The old `internal/hosts` store runs on them unchanged. |
| `pause_state` | the files `paused` and `paused.<id>` | `target` is a resource id or `*`; a row means paused. |
| `applied_definitions` | `runtime/applied.json` | Digests only, never definitions. |
| `credential_issuance_receipts` | `credential-issuance/<id>/<state>.json` | One row per issuance and state, written once; `refs` holds `file://` references, never values; `at` keeps RFC 3339 nanoseconds. |

Not carried: the old `projects` and `resources` tables (empty; definitions live in the descriptors) and
`schema_migrations`. The scheduling tables arrive with the scheduling slice. Reads go through `Reader()`, writes
through `WriteTx`, and nothing writes while a cursor is open (guide section 4).

## Registry

`registry.ForRoot(adopt_root)`: the index is `<adopt_root>/registry.yaml`, read and written in place in the old
format (`version: 1`, pointer entries), because tether sysop reads that file directly. Descriptors stay in their
owning repos and keep the `cerberus-project/v1` schema unchanged; validation messages are the old ones (`port is 0;
omit the port field ...`). The only retired directory refused is `<adopt_root>/projects`; `ForRoot` reads no home
directory and no global `config.yaml`. The home-based constructors (`Default`, `ForConfig`, `IndexPathFor`) stay for
the carried callers until their slices port them.

While the old and new builds both run, both may write the same index. Each write is an atomic rename, but two
registers at the same moment can lose one of them (read, modify, write). Register from one build at a time during
the transition.

## Configuration

Defaults are in the manifest. The operator overrides any key in the YAML file named by `SUBSTRATE_CONFIG`
(planned: `~/.config/cerberus/substrate.yaml`). The merge is the `config` module's.

| Key | Default | Meaning |
|---|---|---|
| `httphost.addr` | `127.0.0.1:4786` | Listen address. Must be loopback (refused otherwise). 4783 and 4785 are the old build's console and mcp-http. |
| `database.sqlite.path` | `cerberus.db` (under the data directory) | The database. |
| `logging.level`, `logging.format` | `info`, `text` | Logging module. |
| `cerberus.install_root` | `~/.cerberus/apps` | Artifact installs and resource logs, adopted in place (plan section 3). Absolute or `~/`-prefixed. |
| `cerberus.adopt_root` | `~/.cerberus` | Files kept in place in the old format because other programs read them: the registry index `registry.yaml` (tether sysop reads it). Absolute or `~/`-prefixed. |

## Shutdown

SIGINT or SIGTERM cancels the context; `httphost.Serve` stops accepting and waits for in-flight handlers; `run`
then stops the modules in reverse start order. Proved with a real process (`cmd/cerberus/main_test.go`). Later
slices add their background work to this drain in the order of plan section 4.4.

## Checks

`go vet ./...`, `go test -race ./...`, `golangci-lint` (new issues on PRs; carried code is linted as it is ported),
`substrate pins check --app .`, the console build before tests, `substrate scan-public --ref HEAD`
(`.github/workflows/ci.yml`).
