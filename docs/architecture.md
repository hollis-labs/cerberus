# Architecture: Cerberus on Substrate

This describes the `substrate-port` branch. The live build is on `main` until cutover. The plan is
`docs/substrate-port-plan.md`; the guide is hollis-labs/substrate `docs/adopting-substrate.md`. This file grows
with each slice and states only what the branch does now.

## Decisions (guide section 0)

| Question | Answer |
|---|---|
| Migrated data or fresh start? | **Migrated.** The app is in daily use; every store reaches the new build, verified (plan section 5; `docs/substrate-port/inventory-data.md`). The new build never opens the old data in place: the import is `cerberus migrate-from` (slice 10). |
| Variant | `app-host`: one process serves the API, the console, MCP over HTTP and the supervision loop. |
| Who issues identity? | Cerberus's own (`identity` module), owner created offline. Auth in enforce mode. |
| Routes | Every `/api/` route has a scope (plan section 4.3); `/healthz` is the only public route. There is no open mount: Cerberus is an outbound client of Outposts (`pkg/outpost`, token files read in place), and the events credential is a file the hub relay reads, not an endpoint. |
| Background work | Supervise mode only: the resource monitor, the host monitor and janitor (`internal/hostmon`), the scheduler and event export (both off by default), plugin processes. App code owns them and stops them in the plan's section 4.4 order (`cmd/cerberus/background.go`). |
| UI | app-shell plus BOM-pinned kits; app nav and surfaces in `ui/app.json` (slice 11). |
| Database | **SQLite at cutover; the schema is dialect-ready** (see Database). Until a table class moves to Postgres, a `database.driver` other than `sqlite` is refused at start. |

## Layout (slices 1, 2 and 4)

| Path | What |
|---|---|
| `cmd/cerberus/substrate.yaml` | The manifest: `app-host`, profile `minimal` plus `database` and `cli`; defaults for every key. |

| `cmd/cerberus/main.go` | Signal context (SIGINT, SIGTERM), `boot.StartWith`, the `cli` root with `serve` (also the default command). |

| `internal/settings` | Decodes the `cerberus:` block; refuses unknown keys and bad values, naming the key. |

The rest of `internal/` and `pkg/` is the old build's code, carried unchanged until its slice moves it
(plan section 4.2). Removed from this branch, readable on `main`, and ported from there by their slices:

- the old `cmd/cerberus` entry and its CLI;
- the packages that depend on `libs/security/webauthn`, which the BOM does not pin until the owner decides
  whether passkey approvals stay: `internal/presence`, and through it `internal/cerbapi`, `internal/app`,
  `internal/mcp`, `internal/webui`, `internal/egress/results`, `internal/conformance` (tests only),
  `internal/smoke/confirmdialog` and `internal/testfixture/sentinel`.

## Data directory

`CERBERUS_DATA_DIR`, otherwise the XDG data home joined with `cerberus-substrate`
(`~/.local/share/cerberus-substrate`, a sibling of the old build's `~/.local/share/cerberus`). Resolved in the
`AfterConfig` hook. A relative path in the config (the manifest default `database.sqlite.path: cerberus.db`) is joined
onto it; an absolute path from the override is kept; a relative path that leaves the directory is refused.

The directory is created `0700` only if it is missing. An existing directory is never changed: one that others can
read or enter is refused with the `chmod` to run. The database file is likewise created `0600` only if missing, and
an existing one with a looser mode is refused.

The directory never overlaps the old build, so both run side by side: the old build keeps `~/.cerberus` (state
tree) and `~/.local/share/cerberus` (its `workspaces/<ws>/main.db`).

### Legacy guard

`internal/datadir`. A refused start changes nothing, under the old homes or anywhere else: every check runs before
anything is created, and none of them writes.

In `AfterConfig`, before the data directory is created:

- `RefuseOldPaths`: the data directory or the database path is, or is inside, either of the old build's homes:
  `~/.cerberus` and the old XDG data directory (the XDG data home's `cerberus`). Symlinks are followed.
- `RefuseOldContents`: the data directory holds `workspaces/` (the old XDG layout) or an entry of the old state
  tree (`daemon.lock`, `cerberus.sock`, `cerberus.pid`, `registry.yaml`, `plugin-connectors.json`, `audit`,
  `approvals`).

In `Before["database"]`, immediately before the module opens (and would migrate) the file: the path check again,
then `RefuseOldSchema`. An existing file is opened `mode=ro&immutable=1`: no lock, no WAL replay, no checkpoint, and
no `-wal` or `-shm` created or removed. It is refused if it has a `schema_migrations` table (the old store's; goose
never creates one), or if it cannot be read that way.

## Database

Dialect-ready, and the cutover runs on SQLite (plan section 5.1). Every store access goes through the `database`
module (libs `core/store`), via `storage.FromApp(app)`, which hands out one store per table class:

- `Stores.Local`: class A, local state that must work while Postgres is down. Always the local SQLite store.
- `Stores.Telemetry`: class B, the host-monitoring tables. Today the same store. After acceptance it may become a
  named Postgres store (Substrate's `database.Named(app, "data")`). That switch is made in `FromApp` alone.

There is one goose set per dialect: `internal/storage/migrations/sqlite` and `.../postgres`, with the same
versions (a parity test checks this). `00001_local.sql` holds class A and `00002_telemetry.sql` holds class B,
which moves to the named store's set when B moves. Until the first release each file is edited in place. SQL goes
through `Dialect().Rebind`, and the store tests run on SQLite and on Postgres:
- CI starts a `postgres:17` service and sets `SUBSTRATE_TEST_POSTGRES_DSN`;
- locally, without that variable, the Postgres runs skip and say so.

The module migrates under its open lock, so a start on an empty data directory creates the schema and a second
start is a no-op (tested on both dialects, and with the real binary in `cmd/cerberus`).

| Table | Class | From the old build | Notes |
|---|---|---|---|
| `pause_state` | A | the files `paused` and `paused.<id>` | `target` is a resource id or `*`; a row means paused. |
| `applied_definitions` | A | `runtime/applied.json` | Digests only, never definitions. |
| `credential_issuance_receipts` | A | `credential-issuance/<id>/<state>.json` | One row per issuance and state, written once; `refs` holds `file://` references, never values; `at` keeps RFC 3339 nanoseconds. |
| `host_samples`, `host_status`, `host_sample_rollups`, `host_rollup_state`, `host_events` | B | `main.db`, same columns (migrations 006 to 008) | The SQLite tables match the old migrations column for column (frozen in `internal/storage/testdata/old`). The old `internal/hosts` store runs on them unchanged. |

Not carried: the old `projects` and `resources` tables (empty; definitions live in the descriptors) and
`schema_migrations`. The scheduling tables arrive with the scheduling slice. Reads go through `Reader()`, writes
through `WriteTx`, and nothing writes while a cursor is open (guide section 4).

## Registry

`registry.ForRoot(adopt_root)`: the index is `<adopt_root>/registry.yaml`, read and written in place in the old
format (`version: 1`, pointer entries), because tether sysop reads that file directly. Descriptors stay in their
owning repos and keep the `cerberus-project/v1` schema unchanged; validation messages are the old ones (`port is 0;
omit the port field ...`). The only retired directory refused is `<adopt_root>/projects`; `ForRoot` reads no home
directory and no global `config.yaml`. The home-based constructors (`Default`, `ForConfig`, `IndexPathFor`) stay for
the carried callers until their slices port them.

## Supervision

`cerberus.mode` is `observe` (the default) or `supervise`. The lane (`internal/supervise`) reads the registry's
resources fresh on every call. In both modes it reports each one:

- an `os_service` supervised by `systemd_user` (or `auto` on Linux), Cerberus-written or a native unit named by
  `service_name`: its state from `systemctl --user show <unit>`;
- a `dev_session`: its state from this build's `<data dir>/pids/<id>.pid` and `.meta`, checked against the running
  process's start identity. The new build never reads or writes the old tree's `pids/` or `locks/`
  (`internal/service.SetStateRoot`); it learns old's sessions only from `standby.d/sessions.json` (plan 7.1).
- anything that is not a local process (an ssh server, a container): unobserved, a named handle.

**Observe mode** refuses `apply`, `deploy`, `stop`, `reload`, `sync` and `remove` (L7, L8) with 409 `observe_mode`,
before anything else. It writes nothing anywhere and starts no background work.

**Supervise mode** runs the old build's six mutations with the old build's results (`supervise.Mutate`):

1. the acknowledgment, before the resource is looked up: 409 `acknowledgment_required` without it;
2. the approver (`supervise.Approver`). Until slice 6 it is `InterimApprover`: an acknowledged request passes; a
   request naming an approval, a plan or a confirmed plan is refused 428 `approvals_unavailable`, and a target a
   lockdown or freeze in `<data dir>/brakes` covers is refused 423 `approvals_unavailable`. The table it is tested
   against (`supervise/approvertest`) is the old build's routing, and slice 6 reuses it. A configured policy
   (`<config dir>/cerberus/policy` not empty) refuses the start in supervise mode, since nothing would enforce it;
3. the run. Every failure after the gate is 200 `{success:false, error}`: an unknown or non-local resource, a port
   conflict, the self-guard, a build lock, build, install and apply failures. Deploy and apply add the config and
   dependency warnings and redact their output through the resource's redactor, as old did.

A dev session's `stop` and `remove` record the pause, and `apply`, `deploy` and `reload` clear it, in the class A
store (`pause_state`), never in `~/.cerberus/paused.<id>`. A successful `apply`, `deploy`, `reload` or `sync`
records the definition's digest (`applied_definitions`), keyed with `<data dir>/audit/.digest_key`, the key the old
audit chain digests with once it is copied (plan section 6), so a digest migrated from `runtime/applied.json`
compares equal. The key's fingerprint is recorded beside the digests (`applied_digest_key`, written by the
migration with the digests it imports, or by the first supervise start on an empty store), and supervise mode refuses
to start when digests exist and the key is missing or has another fingerprint; it never creates a key over migrated
digests. There is no `start` verb: the old build has none, and `apply` starts.

The resource monitor (supervise mode only) restarts a dev session with `auto_restart` that went down, as old's did:
not while paused or frozen, within `max_restart_attempts` and `restart_cooldown`, and only the definition last
applied. It stops no workload. Until slice 6 a restart is not recorded in an audit chain.

`cerberus.self_resource_id` names the resource this process runs as (`cerberus-substrate`, plan section 7.2 C). At
start the process reads `/proc/self/cgroup`: running in a systemd unit other than the one that resource installs as is
refused, and so is an id the registry does not list. A process outside any service unit (run from a shell) starts,
with a warning in observe mode; supervise mode refuses it, since a hand-run copy beside the unit would be a second
writer. In supervise mode every verb on that resource is refused (200 `success:false` naming fleet-install), through
the lane and through the connector's mutation guard.

### Unit renderer parity

`local.RenderSystemdUnit` renders the unit a resource installs as without writing it. Its output must be byte for
byte what the old build writes, or the first `apply` after the handover rewrites and restarts the workload.
`internal/connector/local/testdata/parity` holds synthetic descriptors and the units the old renderer on `main`
produces for them (how to regenerate is beside them). `TestRendererMatchesRealUnits` compares against the host's
real unit files, taken into `$CERBERUS_PARITY_FIXTURES` at rehearsal and never committed.

While the old and new builds both run, both may write the same index. Each write is an atomic rename, but two
registers at the same moment can lose one of them (read, modify, write). Register from one build at a time during
the transition.

## Identity, scopes and the API

`identity` and `auth` (enforce) are in the manifest. The signing key `identity.key_file` is anchored in the data
directory like the database. The owner is created offline (`cerberus identity setup`, password on stdin). Machine
callers get API keys (`cerberus identity key create`).

`internal/api` holds every route in one table with the scope the guard enforces:
- `cerberus.read`, `.operate`, `.admin` and `.approve` (plan section 4.3);
- the mux and the scope table are both built from it;
- `Validate` refuses a route without a known scope, so a handler cannot be served unscoped;
- a path not in the table is refused by the guard (`403 route_not_mapped`).

Served today:
- the legacy-route set L1 to L9 under `/api` (`docs/substrate-port/legacy-routes.md`, an approved cross-app
  contract), with the old shapes, held byte for byte to the old types by goldens;
- the approve routes, registered with `cerberus.approve` and person-only.

Observe mode:
- reads come from the registry under `cerberus.adopt_root`, and from `hosts.yaml` and `state/hosts.json` there, all
  read in place;
- runtime state comes from an `Observer`: the supervision lane, through `laneObserver` (`cmd/cerberus/observer.go`). L3 carries a systemd unit's `systemd_*` fields from its show record;
- mutations answer `409 observe_mode`.

**Approve.** `cerberus.approve` is the owner's console identity session only (decision 0.1). Two rules enforce it:
- The approve routes accept only the identity module's session principal (kind `user`, a session id, no token id
  or parent). An API key, any token minted at `/api/token` (from a key or from the owner's own session), and local
  trust get `403 user_required`.
- No machine credential may be minted with `*`, `cerberus.*` or `cerberus.approve`. `api.KeyGuard` refuses this on
  `POST /api/identity/keys` and `/api/identity/pairing-codes`, and the offline `identity key create` refuses the
  same scopes.

Order of the handler, outermost first: `api.KeyGuard`, then `identity.Middleware` (cookie to bearer, with
`X-Requested-With` and a same-origin `Origin` on cookie writes), then the host (guard, routes).

## Configuration

Defaults are in the manifest. The operator overrides any key in the YAML file named by `SUBSTRATE_CONFIG`
(planned: `~/.config/cerberus/substrate.yaml`). The merge is the `config` module's.

| Key | Default | Meaning |
|---|---|---|
| `httphost.addr` | `127.0.0.1:4786` | Listen address. Must be loopback (refused otherwise). 4783 and 4785 are the old build's console and mcp-http. |
| `database.sqlite.path` | `cerberus.db` (under the data directory) | The database. |
| `logging.level`, `logging.format` | `info`, `text` | Logging module. |
| `cerberus.install_root` | `~/.cerberus/apps` | Artifact installs and resource logs, adopted in place (plan section 3). Absolute or `~/`-prefixed. |
| `cerberus.mode` | `observe` | `observe` (read and report, refuse every mutation) or `supervise` (slice 5; refused for now). |
| `cerberus.self_resource_id` | empty | The resource this process runs as; checked against its systemd unit at start. |
| `cerberus.adopt_root` | `~/.cerberus` | Files kept in place in the old format because other programs read them: the registry index `registry.yaml` (tether sysop reads it). Absolute or `~/`-prefixed. |
| `cerberus.cli_key_file` | `~/.config/cerberus/cli.key` | The API key the CLI presents as a bearer to `http://<httphost.addr>/api`. Created offline (`cerberus identity key create --out`). |

## Shutdown

SIGINT or SIGTERM cancels the context. In the order of plan section 4.4: `httphost.Serve` stops accepting and waits
for in-flight handlers; the resource monitor stops (it runs on a context the signal does not cancel, and stops no
workload: an `os_service` unit and a dev session outlive the process); `run` then stops the modules in reverse start
order. Proved with a real process, a fake `systemctl` on PATH and SIGTERM (`cmd/cerberus/main_test.go`). Later slices
add the scheduler, host monitor and plugins to this drain at their steps.
